### Observed (named calls, literals and control flow that the decompiler shows directly)
- `codenav.GetUsages` (0x83b2f60): builds request and request-state attributes for tracing, converts the usage kind to a string (definition, reference, implementation style kinds) and wraps the call in an observation that reports slow requests against `serviceObserverThreshold`. It then calls `initializeVisibleUploads` once, and then loops. Each loop iteration calls `gatherLocalUsages`, then `localPhaseDidNotMakeProgress`; the logging fields in the loop are the literals `iteration` and `numUsagesGathered` (the literals are truncated to 8 and 16 characters in the binary's string table view, so the exact spelling is inferred from those prefixes and lengths 9 and 17). There is a comparison of a 6-byte string against the bytes for the word `remote` (0x6f6d6572 followed by 0x6574, little endian), and on a match it calls `symbolsToMonikers` and then `gatherRemoteUsages`. So the loop has at least a local phase and a remote phase selected by a named strategy value.
- `localPhaseDidNotMakeProgress` (0x83b59a0): a pure guard. It compares two integer pairs from its argument structs (looks like a previous count versus a current count, and a current iteration versus a limit). If progress was made it returns 0. If not, it logs four integer fields and a message (the string is 0x26 characters long) and returns 1. Observed: the function logs and returns true only in the no-progress case; which integers they are is inferred, not observed.
- `gatherLocalUsages` (0x83b6960): works with sets of strings (set add, sorted set values), builds an extractor through `extractorFor` and `LocationExtractorNamedFunc.Extract`, converts paths with `NewUploadRelPath`, and fetches the actual locations through `getUploadLocations`. So local gathering means: for each visible upload, extract the wanted locations (by kind) from the upload's stored SCIP data, deduplicated by path.
- `gatherRemoteUsages` (0x83b7b60): first calls `prepareCandidateUploads`, returns early (empty) when there are none, records the trace attribute `uploadIDs`, runs an operation labelled `RemoteSymbolSearch`, builds a map keyed by an integer id (upload id) holding per-upload data, calls a function stored in the service (the upload or lsif store interface, through an indirect call) with the symbols, and finally calls `getUploadLocations` for the uploads it found. A cap check (`if limit <= count then reset cursor`) clears the continuation once enough results are gathered.
- `PreciseUsagesV2` (0x83b99e0): wraps in an observation, creates a gitserver pool (`boundary.NewGitserverPool`), a `GitTreeTranslator` per repository (translates ranges between commits), resolves the symbol (`ResolvedSymbolComparator.TryGetNavSymbol`), then `discoverUploadsAtOrigin` and `NewOriginOnlyNavPlan`, then `discoverRelationships`, builds repository metadata (`buildRepoMetadataMap`), checks API errors, collects a set of completed upload ids, applies sub-repository permissions (`authz.DefaultSubRepoPermsChecker`), and finally streams results through `NavPlan.Stream`, with `newPreciseV2Cursor` and `loadPreciseV2Cursor` for paging. A debug assertion switch (`lib/core.assertionsEnabled`, `panicWithContext`) guards type assertions.
- `findCandidateOccurrencesViaSearch` (0x83c6a80): runs a search through `executeQuery`, keeps only results of type `TYPE_FILE`, converts each result range to a SCIP range (`scipFromResultRange`), takes the surrounding line (`lineForRange`, `surroundingContent`), and groups results by repository-relative path and commit into `matchedFile` / `candidateMatch` collections. It raises an error if the query result is of an unexpected shape.
- `searchBasedUsagesImpl` (0x83ccda0): calls `searchBasedCandidateMatches` (which uses the function above), then maps each `candidateMatch` into a `SearchBasedMatch` (`matchedFiles... Map`). It reads site configuration (`internal/conf`), most likely for a search timeout or limit.
- `syntacticUsagesImpl` (0x83c9f00): builds a language filter (`NewLanguageFilter`), finds the symbol at the requested range (`symbolAtRange`), runs a search with `executeQuery` restricted by an upload/repo allowlist (`dbfilter.NewAllowlist` over int32 ids), accepts only `TYPE_FILE` results ("Unexpected match type" otherwise), and logs `Final result: %+v` and the word `completed`. So the syntactic tier is also driven through search, with the syntactic index consulted to restrict the allowed files or repositories (the exact use is inferred).
- `FindClosestCompletedUploadsFromGraphFragment` (0x8416b80): builds a commit-graph view from the database (`scanCommitGraphView`), constructs `commitgraph.NewGraph`, and then, for the requested commit, looks up that commit's nearest-upload entries. It converts each upload id plus a distance (the map value plus an offset taken from the requested commit's own entry) and builds a SQL fragment per upload id, then runs a second query with `makeFindClosestProcessUploadsConditions` ANDed together, and scans completed uploads (`scanCompletedUploads`). It logs `numCommitGraphKeys` and result counts; the log marker text is the placeholder `TODO Domain Owner`.
- `makeNearestUploadsQuery` (0x84398a0): builds one SQL fragment per commit string, joins them with a separator, and formats a larger SQL template (length 0x291) using the repository id and the joined list. It is a pure string and parameter builder.
- `commitgraph.NewGraph` (0x840cc80): takes a map from commit to its parents and a set of commits that have uploads, calls `populateUploadsByTraversal` (propagates "which uploads cover this commit" through the graph, nearest first), then builds a second map from each commit to a (nearest commit, distance) pair where distance is incremented by one per step through parents, sorts the commit ids (pdqsort of strings), and returns a struct holding the sorted commit list, the traversal result and the distance map.
- `handleRawUpload` (0x844f440): opens the upload as a gzip-compressed file named by pattern `upload-%d.lsif.gz` (a temporary file), creates an index reader (`newIndexReader`), classifies a missing-revision error as `errCommitDoesNotExist` (via `errors.HasType` on the gitdomain RevisionNotFoundError), then calls `prepareSCIPDataStream`, `writeSCIPDocuments`, `isUniqueConstraintViolation`, `collectPackageData`, `runHooks`, and records `observeUploadStoreTransactionDuration`. A literal `rewritin...` (truncated) suggests a rewriting step of the upload (inferred).
- `collectPackageData` (0x8451240): seeks the index reader to the start, runs a visitor over the SCIP index (callback `collectPackageData_func1`) that fills a processed-package-data struct (packages and package references), then `ProcessedPackageData.Normalize` (dedupe or sort). Nothing else: it is a single pass over metadata.
- `writeSCIPDocuments` (0x8455cc0): sets up a closure `writeSCIPDocuments_func1`, passes it with a timestamp (`time.Now`) to a transaction callback on the store, records the duration outcome (`observeCodegraphTransactionDurationOutcome`) with different outcome labels for success, error and unique-violation, and on success records upload volume (`observeCodegraphUploadVolume`, two counters from a small result struct). So writing documents is one transaction, with the unique-violation outcome treated as its own label rather than a failure (matches pass 3).

### Inferred (reasoned from the observed calls, not seen directly)
- The "ladder" in my pass 3 note was only partly right. Inside `GetUsages` the observed loop is local then remote, repeated per iteration, with a progress guard that stops the loop when an iteration adds nothing. The syntactic and search-based tiers are not called from `GetUsages` itself in this decompilation; they are separate implementations (`syntacticUsagesImpl`, `searchBasedUsagesImpl`) that some outer caller must select when precise data is missing. I have not yet verified the caller (use `procedure_callers` for `searchBasedUsagesImpl` and `syntacticUsagesImpl` to settle it).
- Freshness works by distance: the commit graph assigns each commit its nearest indexed commit and a distance; the query orders or filters uploads by that distance. Results from a farther commit are then moved to the requested commit by the `GitTreeTranslator` (range translation using diffs), which is how a stale index still answers for a newer commit.
- Both fallback tiers lean on the search backend to find candidate lines and only then use structure (a SCIP range, a symbol at a range) to refine. Precision therefore ranges from "exact symbol relations" down to "string match with a syntactic filter".

### What Falkon could borrow (observations only; no proposals)
- A progress-guarded loop for graph-style lookups: gather, check "did this round add anything", stop. Cheap and bounded, and it logs the iteration and count so you can see why a lookup ended.
- Nearest-indexed-commit lookup with a stored distance, plus range translation from the indexed commit to the asked commit. This maps directly onto Falkon's per-revision builds and head pointer.
- Treating a duplicate-write conflict as a labelled outcome instead of an error, which keeps ingest idempotent and the metrics honest.
- Search-first candidate discovery followed by structural refinement, restricted by a file or repo allowlist, as the lowest tier. Falkon already has Zoekt, so this is the same shape.
- Results paged through an opaque cursor, with a permission check applied before streaming (sub-repository permissions in Sourcegraph's case).
- Single-pass metadata collection (packages and references) separate from document writing, so cross-repo links can be built without re-reading document bodies.

## Pass 5: tier entry points and the nearest-upload SQL (worker binary, REA/Ghidra, 2026-10-25)
Observed:
- The three tiers are separate service methods on the same code-navigation service: `SearchBasedUsages` (0x83b20a0, calls `searchBasedUsagesImpl`), `SyntacticUsages` (0x83b0de0, calls `syntacticUsagesImpl`) and the precise `GetUsages` / `PreciseUsagesV2`. None of the three has a statically resolved caller in this worker binary (they are reached through an interface or a remote call). So the choice between tiers is made outside this binary, most likely in the frontend's usages resolver, which is the next thing to read in the frontend binary.
- The nearest-upload data is precomputed in Postgres, not computed at query time. There is a table of nearest uploads per repository and commit, holding a JSON object that maps upload id to a distance, and a links table that points a commit at an ancestor commit with an extra distance. The query reads the direct rows for the requested commits and unions in the linked rows with distances added, so a commit with no direct row inherits its ancestor's uploads with the distances summed.
- A second step turns upload ids into a token made from a hash of the upload's root directory plus its indexer name (with the scip- and lsif- prefixes stripped, so an LSIF and a SCIP index from the same tool count as the same indexer). That token is how the service deduplicates "the same index from different commits" and keeps the closest one.
- Eligibility is a database view: uploads must be in a "navigation eligible" view, and a visible-at-tip table with a default-branch flag marks whether an upload covers the repository tip. Upload rows carry state, failure message, start and finish times, a process-after time, reset and failure counters, indexer and version, and an associated index id.
Inferred: the ancestor links are maintained by a background job that walks the commit graph (the `NewGraph` traversal seen earlier) and writes the nearest and links tables, so reads are cheap and writes carry the graph cost. Not yet confirmed by reading the writer.
Unknown: the writer job; the tie-break when several indexes have equal distance; how "nav eligible" is defined.

### Observed: how usages are served (tier choice)
- The GraphQL resolver `UsagesForSymbol` (codenav transport) first checks a site setting for "SCIP-based APIs enabled" and returns a not-enabled error if it is off. It resolves the arguments, then calls three wrappers in a fixed order: `preciseUsages`, then `syntacticUsages`, then `searchBasedUsages`.
- The paging cursor carries the current phase as a string. The phase names found in the code are `preciseV2Start`, `preciseV2InProgress`, `syntactic`, `searchBased` and `done`, with helper methods `IsPrecise`, `IsSyntactic`, `IsSearchBased`, `IsDone`, `AdvanceCursor`. The resolver compares the phase against these strings, runs the matching tier, and after each tier checks whether the requested page size is full; if not, it falls through to the next tier.
- The GraphQL argument also names a provider with the values `PRECISE`, `SYNTACTIC`, `SEARCH_BASED` (strings present), so a caller can ask for one tier.
- Consequence: the "ladder" is real and it lives in the resolver, driven by a cursor, so a client pages through precise results first, then syntactic, then search-based, in one continuous stream.

### Observed: the agent loop (shape only)
- `Run` loops: estimate the prompt size, run one turn, then if the model asked for tools it first splits off "deferred" tool calls (tools whose result comes from outside, such as asking the user), executes the rest with `executeTools`, wraps the outputs into a tool-results message, and goes round again; with no tool calls it extracts the final text. An error type `ErrExternalResultHandoffSave` exists for saving state when a turn must wait for an outside answer.
- `runTurn` (about 19 KB of code, the biggest function here): checks and if needed compacts first (`compactIfNeeded`), then calls the model (`callLLM`). If the answer says the prompt was too long (`isPromptTooLong`) it calls `recoverFromPromptTooLong`; otherwise it processes the streamed response parts, records usage statistics, builds turn telemetry, and estimates the next prompt size. `doFinalSummarization` exists for forcing a final answer.
- Prompt size estimate: the sum of the characters of all tool schemas plus all message parts (text, tool-call arguments, tool results), divided by 3.5, as a token count. It is a cheap character estimate, not a tokenizer.
- `compactIfNeeded`: does nothing if no compactor is configured; returns an error if no input limit is configured; otherwise asks the compactor whether the current estimate against the limit warrants compaction (the reason label is an 8-character word, likely "proactive"), and if yes runs `compact`.
- `compact`: a traced step (`agent.Run.compact`) that calls the compactor to rewrite the conversation, records a counter and a duration histogram labelled by workload and outcome, replaces the history, re-estimates the prompt size, emits an event, and sets a "compacted this turn" flag. A summary-turn type for stored compactions (`compactionSummaryTurn`) and a token reserve constant (`compactionReserveTokens`) exist.
- `recoverFromPromptTooLong`: if no compactor is configured, or this turn was already compacted, it gives up and returns the best final text so far. Otherwise it logs a warning with two integers and the error, runs `compact` with the reason `prompt_...` (15 characters, most likely `prompt_too_long`), decrements a retry counter, and returns "retry". So compaction is allowed once per turn, and a model refusal for length is turned into compact-and-retry.
- Sub-agents: `executeSubAgent` runs a nested agent (used for the CodeFinder tool) and records sub-agent turn count and task size (`subAgentTurnCount`, `subAgentTaskBytes`); `logSubAgentContextFinished` logs when it ends. Tool results can be shortened with `TruncateMiddle` (keeps the start and end). The last message can be marked for provider prompt caching (`withLastMessageCached`).

### Observed: prompt texts (read from the binary)

## Pass 9: Zoekt ranking, decompiled from `zoekt-webserver` (build sha-490422d, May 2025; NOT the 8.1.1335 build, which has no published Zoekt image)
Method: REA/Ghidra on `zoekt-webserver-sha490422d/zoekt-webserver`. This binary carries DWARF with Go source file names and line numbers (score.go, contentprovider.go), so function names and parameter lists are reliable. Constants below are floating point literals read from the decompiler output; the sequence in which they are applied is read from control flow. Because the binary is a year older than the rest of the study, treat all numbers as "how it worked in May 2025".
Observed:
- File-level score (`indexData.scoreFile`, score.go line 301): (1) count how many query atoms (terms) matched in the file and add `(1 - 1/n) * 400` under the label "atom", so matching more distinct terms adds up to 400 but with diminishing returns; (2) nudge every line match and chunk match score by `1 - position/total` (earlier matches in a file score slightly higher) and remember the best one; (3) add the best line or chunk score as the "fragment" score; (4) truncate the sum to a whole number; (5) final score = file score times 10,000,000 plus repository rank times 100 plus a document-order term `(1 - docIndex/numDocs)` times 10. The repository rank is a 16-bit number stored in the repository's index metadata (set by the indexer, in Sourcegraph's case from a popularity signal). So content relevance always dominates, repository rank decides ties between equally relevant files, and index order decides the rest. The debug string it builds reads: score, repo-rank, file-rank.
- Line-level score (`contentProvider.scoreLine`, score.go line 97), per match on a line: word boundary check using five character classes (lower case letter, upper case letter, digit, quote or punctuation, other, whitespace). A match with a boundary change on both ends is a "WordMatch": +500. A boundary on only one end is a "PartialWordMatch": +50. If the match sits on a symbol found by the ctags data: the match is exactly the symbol: +7000 ("Symbol"); it covers the start or end of the symbol: +5500 ("EdgeSymbol"); it only overlaps: +4000 ("OverlapSymbol"). In addition the symbol kind adds a language-specific weight (see next). For file names: the match is the file's base name: +7000 ("Base"); inside the base name: +4000 ("InnerBase"); at its edge: +5500 ("EdgeBase"). Then the line score is multiplied by the match's own boost factor. A parallel function `scoreLineBM25` produces a "tfScore" and the search option `UseBm25Scoring` switches the whole flow to a BM25 path (`scoreFileBM25`).
- Symbol kind weight (`scoreSymbolKind`, contentprovider.go line 647): a table per language (Go, Java, Kotlin, Ruby, Python, C, C++, PHP, Scala, GraphQL, Markdown seen), mapping a ctags kind to a number from about 1 to 10, then multiplied by 100. For example in Go the type or struct kinds and exported functions score highest; an upper-case first letter (exported name) adds 0.5; a file ending in `_test.go` multiplies the result by 0.8; an unknown language gets 1.0 for every kind except a small default table (class-like kinds 10, function-like around 7 to 9). Markdown headings are weighted low (about 2 to 4).
- Diversity step (`boostNovelExtension`, contentprovider.go line 912): after sorting, it collects the file extensions of the top N results (N is a boost offset). It then scans the remaining results whose score is at least a given ratio of the top score and, for the first one whose extension is not already among the top N, moves it forward ahead of the other candidates. The effect is that a result of a different file type can surface near the top instead of ten files of the same type.
- Chunk-level scoring (`scoreChunk`, score.go line 41): groups candidate matches by line, scores each line, keeps the best line (reports "line N" in debug output) and returns the symbols found.
Inferred: because the score for a word-level symbol hit (7000) dwarfs a plain substring hit (0 to 500), a query for an identifier lands definitions first, then other mentions, then partial matches; because file-level atoms are capped at 400, term coverage is a tiebreaker beside the symbol and filename signals, not a driver.
Unknown: what boost value individual matches carry (from query parsing), the default of the BM25 switch in the product, how the 2026 version differs, and the repository rank source for a given deployment.

## Pass 11: natural-language (NLS) search ranking in the frontend (REA/Ghidra on `frontend`, 2026-10-27)
Method: decompiled `applyBoosts` (0xb367620), `concatAndLimit` (0xb3690a0), `tokenizePattern` (0xb36c0c0), `tokenizeTerm` (0xb36da00), `NewBasicQuery` (0xb36cd60), `getSearchType` (0xb36cc20), `addOrUpdateCount` (0xb36a600), `newSearchJob` (0xb369c60), `searchJob.Run` (0xb36a9c0), `isLikelySymbol`, `stemTerm`, the package `init` functions, and read the literal bytes that those functions point at. Same caveat as before: no Go types, so call order, literals and plain comparisons are trusted and struct layouts are not. `boostedJob.Run` (0xb368780) was read only through its callee list.

### Observed
- The NLS "search type" is a request parameter named `type` with exactly four accepted values: the empty string, `code`, `path` and `text` (an unknown value is an error built with the library's `Newf`). The type chooses which extra query parameters are appended to the search: the empty type adds two parameters, `type:path` and `type:file`, so both file names and file contents are searched; `path` adds only `type:path`; `code` adds `type:path`, `type:file` and a `file:` filter that is negated and made from a "text file" regular expression; `text` adds the same two plus the same `file:` filter not negated. So `code` means "exclude documentation-like files" and `text` means "only documentation-like files".
- The text-file filter is built once at start-up from a set of 18 extension strings (map `textFileExtensions`, whose visible members include markdown, mediawiki, wikipedia, php3 to php7, phps, phpt and a few build-file names), joined with `|`, and wrapped with a leading regular-expression prefix and a trailing `)$`. The exact leading characters were not read.
- Before any query is built, `addOrUpdateCount` sets or overwrites a parameter named `count` to the integer 5000 (it replaces an existing `count` parameter, otherwise appends one). So each NLS sub-search asks the backend for up to 5000 matches before the merge step cuts the list.
- `parseQuery` rejects boolean operators: the binary contains the error text "nls.parseQuery does not support boolean operators". A query that parses to no patterns and no parameters returns a no-op job.
- Tokenisation is two functions. `tokenizePattern` trims the input, then walks it rune by rune: a double quote toggles a quoted mode; a quoted phrase is kept as one token without further processing, and whitespace outside quotes ends a token. Every unquoted token goes through `tokenizeTerm` and the results are appended to two lists (a list of terms and a list of what looks like symbol or exact-phrase candidates; which list is which was not proven).
- `tokenizeTerm` first splits a token with the separator regular expression `[:#]|->` (colon, hash or arrow, so `pkg::Name`, `file#anchor` and `a->b` become separate pieces). Each piece is trimmed of leading and trailing punctuation (`unicode.IsPunct`). A piece that contains a dot, or that `isLikelySymbol` accepts, is treated as an identifier. `isLikelySymbol` returns true when the piece contains one specific single character (an underscore is the likely character, its byte was not read) or matches the camel-case regular expression `[a-z][A-Z]`. A stop-word map of 222 entries exists (`stopWords`, built in `map.init.1`; the words themselves were not read) and a Snowball stemmer for English (`stemTerm`, language string `english`) returns the stem only when the stem is different from the input. The exact order in which stop-word removal, stemming and identifier handling are applied inside `tokenizeTerm` was not recovered.
- `NewBasicQuery` turns the pattern list and the parameter list into a search query: every pattern becomes a pattern node, every parameter becomes a parameter node, the patterns are combined under one operator node (the operator kind constant is 0, which in this query library is the OR kind, inferred), and the result passes a fixed pipeline `query.For(3)` of normalising transformations and is converted to a basic query. So an NLS search is "any of these terms", with ranking left to the backend.
- `applyBoosts` takes the basic query plus a list of up to a few extra repository names and returns a list of basic queries to run, in this order: first (when the query contains a "repo boost" predicate) a copy of the original query with an added `repo:` parameter holding the union of the boosted repositories' regular expressions; second (when a "repo boost relevant" predicate flag is present) a copy restricted to the extra repositories, each quoted with regular-expression escaping and wrapped as `^name$`; and last the original, unrestricted query. Observed: boosting is done by running restricted copies first, not by numeric weights.
- `searchJob.Run` starts a trace span, launches two tasks in a concurrency pool (the two pool functions `func2` and `func3` each return a result record with matches, stats, error and alert), waits for both, and then calls `concatAndLimit` with the first result list, the second result list and the job's limit (read from a field of the job). Observed in `concatAndLimit`: it loops over the two lists in that order, stops adding once the number of kept results reaches the limit, and drops any result whose key already appeared (a hash map keyed by the result's key method, so duplicates are removed and the earlier list wins). It also merges the two stats records and keeps the later of two timestamps. So the merge order is "first list, then second list, de-duplicated, cut at the limit".
- `boostedJob.Run` maps over child jobs with a parallel mapper (`conc/iter.Mapper`), merges their stats with `streaming.Stats.Update`, and starts a span; it runs the query variants that `applyBoosts` produced.

### Inferred
- The two tasks inside `searchJob.Run` are most likely one search over the original query and one over a second form of the query (for example the identifier-style tokens), but the decompilation does not show which query each task uses.
- The final order a user sees is therefore: results of boosted (repository-restricted) variants first, then the unrestricted results, each in the order returned by the backend (Zoekt scoring), with duplicates removed and the list cut at the limit. No NLS-specific numeric score is added in the frontend.

### Unknown
- The text of the stop-word list, the leading characters of the text-file filter, the numeric limit passed to `concatAndLimit`, and which of the two parallel tasks uses which query.

Retry with different wording."; `max_output_tokens` gives "Sub-agent response was truncated by token limits. The sub-agent's model is the named model `CodeFinder` in the inference model registry. The tool name suffix differs between the legacy "MCP" naming and the newer "MCPV1" naming, and on the hosted product a fixed prefix is added.

## Recreation notes (minimum facts, numbers and orderings per component)
Legend: [O] observed in a binary, [I] inferred, [U] not obtainable. Everything here was learned from static analysis of Go binaries; nothing was run. Numbers marked [O] are literal constants or defaults read from the code. Where a number is configuration in the original, the default is given.

### 1. Code-intel upload and the nearest-indexed-commit graph
- Ingest [O]: an upload arrives as a gzip SCIP (or older LSIF) index; the worker streams it, makes one metadata pass that collects the packages the repository provides and the packages it references (with versions), normalises that metadata (dedupe/sort), and writes the documents in one database transaction. A duplicate-write conflict is recorded as its own outcome label and is not an error, so re-uploading the same index is idempotent. Storage re-encodes documents into a compact bundle format with compression, a range codec and content hashing [O, names only].
- Package link tables [O]: `lsif_packages` (scheme, name, version, upload id, manager) and `lsif_references` (same columns) give cross-repository jumps by matching a symbol's package scheme/name/version to the upload that provides it.
- Eligibility [O]: only uploads in a "navigation eligible" view count; a visible-at-tip table with a default-branch flag marks uploads that cover the repository tip.
- Nearest-commit graph [O]: build a graph from commit to parents, mark commits that have an upload, then propagate "covered by upload U at distance d" through the graph nearest-first (breadth by one per step through parents) and also record for each commit its nearest ancestor that has data and the distance. Persist two tables: `scip_nearest_uploads(repository_id, commit, uploads{uploadId: distance})` for commits with direct coverage and `scip_nearest_uploads_links(repository_id, commit, ancestor_commit, distance)` for commits that simply inherit from an ancestor. Reads take the direct row, or the link row plus its distance, and the distances are summed [O]. Writes carry the graph cost and run in the background [I]; reads are two indexed lookups.
- Choosing among uploads [O]: uploads are grouped by a token made from a hash of the upload's root directory and the indexer name with the `scip-` and `lsif-` prefixes removed, so an LSIF and a SCIP upload from the same tool count as one; the closest one per token wins. The tie-break for equal distances was not read [U].
- Moving results to the asked commit [I]: a tree translator maps ranges from the indexed commit to the requested commit using diffs, so a stale index still answers for a newer commit.

### 2. Usages tier ladder with cursor
- The GraphQL resolver for usages first checks a site setting that enables the SCIP-based APIs and fails if it is off [O]. It then runs three tiers in a fixed order: precise, syntactic, search-based [O]. A request may force one provider (`PRECISE`, `SYNTACTIC`, `SEARCH_BASED`) [O].
- The page cursor is an opaque value containing the current phase with the names `preciseV2Start`, `preciseV2InProgress`, `syntactic`, `searchBased`, `done`, plus the tier's own cursor [O]. After each tier the resolver checks whether the page is full; if not it advances the phase and runs the next tier in the same request [O]. A client therefore pages through one continuous stream.
- Precise tier [O]: find visible uploads at the origin (the nearest-commit lookup above); run a loop of local gathering then, if the strategy says so, remote gathering by monikers across repositories; stop the loop when an iteration adds nothing ("did not make progress") or an iteration limit is reached; apply sub-repository permissions before streaming; stream through a navigation plan with its own cursor. Definitions, references and implementations are separate "usage kinds".
- Syntactic tier [O]: language filter, symbol at the requested range, then a search restricted to an allowlist of files or repositories from the syntactic index; only file-type results are accepted.
- Search-based tier [O]: candidate lines found through the search engine for the symbol name, each result range converted to a code range, grouped by file and commit, with the surrounding line kept for display.
- Failure behaviour [O]: if the context filter used for permission-like exclusion is invalid, all repository access is blocked (fail closed).

### 3. Zoekt scoring constants (build of May 2025; a year older than the rest) [O]
- Per match on a line: word boundary on both ends +500, on one end +50; symbol hit by ctags data: exact symbol +7000, symbol edge +5500, overlap +4000; plus language symbol-kind weight (1 to 10) times 100 (exported Go names +0.5 before scaling, `_test.go` files times 0.8, unknown language 1.0 for most kinds); file-name hits: base name +7000, edge of base +5500, inside base +4000; then multiplied by the match's own boost factor.
- File score: distinct query atoms matched adds `(1 - 1/n) * 400`; every line/chunk score is nudged by `1 - position/total`; the best line or chunk score is added; the sum is truncated to an integer; final = `fileScore * 10,000,000 + repoRank(16-bit) * 100 + (1 - docIndex/numDocs) * 10`. Content relevance always dominates, repository rank breaks ties, then index order.
- Diversity step [O]: after sorting, take the extensions of the top N results; among the later results scoring at least a ratio of the top score, move the first one with a new extension forward.
- Alternative BM25 path exists behind a search option (`UseBm25Scoring`) [O]; default unknown [U].

### 4. Hybrid search (indexed plus live)
- Flow [O]: find the commit that the index holds for the branch; compute the paths that differ between the indexed commit and the requested commit with a git diff; run the index search while ignoring those paths; scan the changed files directly with the unindexed searcher; if the index moved while this happened, retry the whole thing. The unindexed searcher reads either a content-addressed snapshot of the repository (blobs cached by hash with pre-warmed generations) or a zip archive fetched from the repository service, with metrics for archive file count and size.
- Result merging for natural-language search [O]: run repository-restricted query variants first, then the unrestricted query, merge in that order, drop duplicates by key, cut at the limit; every NLS sub-search asks the backend for count 5000.
- NLS query building [O]: quoted phrases kept whole; split on whitespace; split each term on `[:#]|->`; trim punctuation; identifier-like terms (contain `.`, an underscore-like character, or match `[a-z][A-Z]`) kept as symbols; English Snowball stemming; stop-word list of 222 words; terms combined with OR; type parameter chooses names-only, names and contents, code-only (negated text-file regular expression over 18 documentation extensions) or text-only.

### 5. Agent loop and compaction
- Loop [O]: estimate prompt size (characters of tool schemas plus messages divided by 3.5); each turn: stop check, optional proactive compaction (only if a compactor and a non-zero input limit are configured, once per turn), call the model, on a prompt-too-long error compact once and retry, process streamed parts (text, thinking, tool calls), accumulate usage, then execute tool calls (tools whose results come from outside the process are deferred and the state is saved with a sentinel error) and feed the results back; when the turn budget is spent run a forced final-summarisation turn.
- Sub-agent contract [O]: required non-zero turn limit (probably 18 for the code finder [I]), default wall-clock timeout 120 s, only four tools (natural-language search, keyword search, list files, read file), result is a text; abnormal ends are mapped to short human-readable notes (turn limit, stopped, refusal, output truncation) or errors (context cancelled, empty response, input too large). Telemetry keys: turn count, duration ms, total tokens, task bytes.
- Middle truncation [O]: keep the first 75 percent of the allowed length and the last 25 percent, cut at character boundaries, insert a marker that states how many characters were removed.
- Compaction record [O]: append-only table per thread with `up_to_turn_id`, the summary text, accumulated statistics of the covered turns and the statistics of the summarisation call; the loader replays `[one user-role summary turn] + [all turns after up_to_turn_id verbatim]`; each new summary folds in the previous one; the summary has six sections (goal and state, decisions made, work completed, failed approaches, unresolved, artifacts); appends are guarded by optimistic checks on the active thread entry and on the previous compaction row; events announce start and completion. Trigger fraction, reserve tokens and the summarisation prompt are not in these binaries [U].
- Where the main agent actually lives (Passes 15 to 17) [O/I]: a question is a row in `deepsearch_question_jobs` (standard database work queue with worker hostname and failure message columns); the frontend only enqueues (new conversation, follow-up, fork) and serves the stream; a separate runner service, not published under any Docker Hub name found, dequeues it, runs the loop and publishes events to a Redis broker. Stream event vocabulary [O]: snapshot, turn_start, turn_delta, thinking_delta, tool_call_delta, tool_call_pending, tool_call_complete, tool_call_progress, turn_complete, title, message_created, title_updated, compaction_started, compaction_complete, done, error. A compaction is also shown in the transcript as a display-only turn with a `summary` string that is never replayed to the model [O]. Per-user quota counters with increment, decrement and adjust exist [O].
- Batch-change coding agent [O]: a different agent, the external `pi` CLI (v1.1.0, shipped inside the frontend image) run on executors from a generated script; compaction is its own setting `{"compaction":{"enabled":true,"reserveTokens":N,"keepRecentTokens":M}}`. Design to rebuild [O]: compact when `contextTokens > contextWindow - reserveTokens` (pi defaults 16,384 and 20,000; Sourcegraph's overrides not read [U]); cut by walking back from the newest entry until about keepRecentTokens are kept, at a turn boundary (summarise a split turn's prefix separately); render tool results to the summariser cut at 2,000 characters; summary is a structured checkpoint (Goal, Constraints, Progress done/in-progress/blocked, Key Decisions, Next Steps, Critical Context), cumulative (an update prompt folds the previous summary in and keeps exact paths); treat a length-stopped or tool-calling summary as failed; also recover after the fact when a provider returns an overflow error or input exceeds the window. Hosted models behind it are Gemini via a Google-format gateway [O].

- Limits [O]: 120 s execution timeout; at most 100 `search.*` calls per script (default, configurable); a second default count of 1000 and a 10 MiB size cap (roles not tied to wording); return value truncated at 100 KB; search results are delivered through callbacks with `stats.matched` and `stats.limitHit`; narrow the query when `limitHit` is true instead of raising the cap; the query language has AND-by-default, literal `OR`, RE2 only, filters `repo:`, `file:`, `rev:` (needs repo), `lang:`, `count:`, negation by leading dash, commit/diff filters (`author`, `after`, `before`, `select:commit.diff.added`), and `matchCount` per file for counting.
- Timeout hinting [O]: searches get a default `timeout:` token when none is present; a slow search reports the remaining time minus 5 s (minimum 1 s) so the model can retry.

### 8. Gitserver hardening
- Only allow-listed git sub-commands, arguments and `-c` config keys may run [O]; git runs as a subprocess, never in-process.
- Fetch [O]: no tags, no fetch-head write, protocol version 2, credential helper cleared, LFS smudge skipped through the environment, thread cap, refspec overrides, optional fsck, extra HTTP headers and TLS config, an SSH agent wrapper for SSH remotes, URL redaction in logs, and a separate classification for "external connectivity" errors.
- Housekeeping [O]: janitor repacks when needed, statistics on commit graph and pack files, access logging, a CPU profile endpoint per repository operation; sync per code host (git and Perforce). Callers (searcher, frontend) never hold repositories; they ask for archives, diffs and blobs over gRPC [I].
