# Why the new arm scores 0.58 on "why" (cycle 19, Haiku, o3-history)

## Summary

1. The new arm `clone-tools-git-history` finds the answering change (commit and pull request) on all 16 "why" questions (18 of 18 change units), but finds the ticket on only 2 of 16 (hist-a-04 and hist-a-10). Every one of its 14 misses is a missing ticket; recall is 0.583 because each question has one change unit and one ticket unit and it gets about half.
2. The reason is a tool gap, not search: the ticket sits in the pull request body (11 cases), and the new arm has no tool that returns a pull request body. The two it got had the key written in a changeset file or a source comment.
3. The pull request arm (0.844) got 10 of the 14 misses right, all through `get_pull_request` (its `tickets` list). `get_provenance` returned an empty ticket list in 18 of its 19 calls (the other had no ticket field), and `search_discussions` never delivered a ticket that `get_pull_request` did not.
4. Neither arm gets the ticket for hist-a-03, hist-a-06 and hist-a-14 (the ticket exists only in Jira) and the pull request arm also misses hist-a-07 (it never opened the pull request that holds the key). A stronger model would not fix the 10 recoverable cases; the missing capability would.
5. Cheapest model-free fix: run both flag sets together and add a one-line recipe to `search_commits`; ceiling about 0.92 on "why", realistic about 0.85 to 0.88. Limits: n is 16, one run each, Haiku.

Scoring facts used (from `tests/eval/score.ts`): recall is the share of gold units hit; a squash-merged commit and its pull request are one unit (hit by the SHA or the pull request number); a ticket is its own unit (hit by key); items beyond the gold never lower recall, they only lower precision. The answer is capped at 20 items; no run in these three arms had more than 16, and the gold was always inside, so no crowding out happened.

## Answers

**(1) How many of the new arm's 14 misses did the pull request arm get right, and by which tool?** Ten: 01, 02, 05, 08, 09, 11, 12, 13, 15, 16. In nine of them `get_pull_request` returned the key in its `tickets` list (source `ticket-pattern`, parsed from title, body or branch). The tenth, 11, came from `get_pull_request` with comments plus `search_discussions` on the key (it found the backend pull request titled with RESTWS-1038). `get_provenance` contributed zero tickets: it was called 19 times; 18 returned an empty ticket list and one had no ticket field, even for the same pull requests whose `get_pull_request` call held a key (for example commit 8ec94d2 / #6210, where `get_pull_request` listed TRUNK-6670). `search_discussions` found a key by itself in no case where `get_pull_request` had not already; in 03, 06, 07 and 14 it found nothing.

**(2) Questions neither arm gets.** Ticket for hist-a-03 (clear abandoned-visit bills), hist-a-06 (release shown on sign-in) and hist-a-14 (conditions vs visit-note diagnoses): the stored data holds no key (empty `tickets`, "Related Issue" empty, no key in any tool result in any arm); spec line 116 says these tickets live only in Jira. hist-a-07 is also missed by both, but it is reachable: spec/c15 say pull request 854's body holds the ticket; the new arm cannot open it and the pull request arm cited 854 without opening it (it opened the sibling pull requests 3353 and 2561 instead). Upper bound for "why" with the present data and tools: 13 of 16 ticket units, and for 13 the key sits in a sibling pull request, so 12 are straightforward.

**(3) Reasoning versus tool or data gap.** Tool gap, with evidence: the new arm's own answer for 01 says "the fix commit and its PR message carry no ticket key, and Falkon only shows unverified keys parsed from messages", which is correct for its tools; its `search_commits` results list `ticketKeys` and `pullRequests` from the message only (`linksSource: message, unverified`), and the descriptions of the new tools never name a way to read a pull request body. The Haiku agent in 01, 03, 05, 08, 09, 12, 15, 16 found the correct commit within 8 to 18 turns and reported honestly that it had no ticket; a stronger model could not call a tool it does not have. Data gap: 03, 06, 14 (Jira-only), and 13 (key in a closed sibling pull request). Plausibly fixed by a stronger model or by better prompting: 07 for the pull request arm (open the pull request you are about to cite), 14 for the pull request arm (search terms and the "not ingested" misreading; the new arm's `search_commits` found both changes in 6 calls, so the problem there is planning plus the whole-word-only `search_discussions`, noted in c15 as parked). Roughly 1 to 2 of the 14 misses are reasoning, 11 tool gaps, 3 data gaps.

**(4) Concrete model-free changes, most useful first.**
1. Run the history tools and the pull request tools in one arm (both flags together). Expected: the 10 pull-request-recoverable misses (01, 02, 05, 08, 09, 11, 12, 13, 15, 16) each add 0.5 (13 adds 0.33), so "why" recall moves from 0.583 to about 0.88 (0.92 if 07 also resolves). The history tools also already found both changes of hist-a-14, which defeated the pull request arm, so the combined arm may beat both.
2. Make `get_provenance` return the tickets that `get_pull_request` already parses for the pull request it links (18 of 19 calls returned an empty list, including where the key existed). Then one call from a commit or a code line gives a ticket (01, 05, 08, 09, 12, 15, 16).
3. Join the stored pull request ticket list into `search_commits` / `list_commits` rows: the rows already carry `pullRequests: [number]` from the message (for example #3406 in 14, #6210 in 01). Adding the verified `tickets` of that stored pull request (marked as coming from the imported body) would give the new arm the key with no extra call, and would need no pull request tool in the arm. This is the single change that helps the history-only configuration.
4. A recipe sentence in the `search_commits` description (the D113 place for hints): "A ticket key is usually in the pull request body, not the commit message; if `ticketKeys` is empty and a pull request number is listed, open it with `get_pull_request`." Targets 07 (pull request cited but not opened) and every (b) row once the tool is present.
5. Extract keys from pull request comments into `tickets` (11: key only in a comment; `includeComments: false` also hid it in 03/06/07, so the agent default matters). Smaller: one question.
6. Not fixable without new data: 03, 06, 14 (Jira). A Jira source would be a feature, not a tweak; do not count them.

**(5) Limits.** n is 16 questions, one run each, one model (Haiku), so single-question swings are 0.03 of "why" recall; the 0.58 and 0.84 are not tightly separated from noise on any one row, but the pattern is the same on 14 of 14 misses (change found, key absent), which is why I trust the diagnosis more than any estimate. Ticket location for the (d) rows rests on the spec's count and on tool results the agents happened to request, not on a direct look at Jira or at the stored pull request tables (I did not query them). The ceilings above assume the pull request arm's recall carries over to a combined arm, which has not been run; the extra tools might lengthen runs or change what Haiku cites. Dataset gold for hist-a-13 and hist-a-14 counts two change units for one ticket, which makes those two rows 0.33 steps.
